## Ответы на вопросы агента, раунд 1

_Картинка 300×300 до ответа `/posts/{id}`, устройство сторов и gate, место загрузки деталей и сортировки в FSD, тесты сверх R-13._

```text
· Противоречие R-2/R-3: детали поста сразу показываются из данных списка,
но URL 300×300 по R-2 появляется только после успешного ответа /posts/{id}.
Что показывать в блоке 300×300 до ответа и при ошибке (а без сети —
всегда)? → Вариант: картинку 300×300 показываем сразу, URL строится из
seed, который уже хранится с постом (чистая функция seed → URL, без
ожидания /posts/{id}). При успешном ответе /posts/{id} URL 300×300
сохраняется в запись деталей, как в R-2 — это формальное обогащение ответа.
Пока картинка грузится — плейсхолдер, при ошибке загрузки (включая
отсутствие сети) — fallback. Обнови R-2 и R-3 в requirements.md и отрази
это в потоке «открытие деталей» в architecture.md.
· Как устроить сторы Zustand? Каждый persist-стор гидрируется отдельно,
gate в app должен ждать все. → Сторы:
- Два стора, по одному на сущность: entities/post (посты, детали по id,
статус загрузки) и entities/favorite (Record<id, addedAt>). Каждый со своим
ключом в MMKV и своим version для будущих миграций.
- Через partialize не персистим транзиентное: статус загрузки и ошибки.
Персистим только данные и флаг «список успешно загружен».
- Селектор отсортированного списка объединяет две сущности, поэтому живёт
не в entities, а в widgets/posts-list (или в features, обоснуй выбор).

Gate:
- В app хук useStoresHydrated: явный список persist-сторов, проверяет
persist.hasHydrated() у каждого и подписывается на onFinishHydration.
Приложение рендерит навигацию только когда гидрированы все.
- С синхронным MMKV гидрация, скорее всего, происходит сразу при создании
стора — проверь это на установленной версии Zustand и опиши в
architecture.md. Gate оставляем явным в любом случае: он фиксирует
инвариант и не зависит от выбора хранилища.
- Тест «до гидрации запрос не уходит» пишем на логику загрузки с моком
негидрированного состояния, а не на гонку с реальным хранилищем.
· Где живёт логика «загрузить детали, если их нет в кэше» и селектор
сортировки (он объединяет post и favorite, а сущностям нельзя импортировать
друг друга)? В R-10 их нет. → - «Загрузить детали, если их нет в кэше» —
features/load-post-details, симметрично features/load-posts. Проверка кэша,
однократный запрос, сохранение деталей и URL 300×300 — всё там.
- Селектор сортировки — widgets/posts-list/model: чистая функция (posts,
favorites) → отсортированный список с флагом isFavorite + хук поверх
сторов. Тест пишем на чистую функцию.
- Карточка поста в entities/post/ui получает isFavorite пропсом и про стор
избранного не знает.
- DetailsScreen в pages/details собирает entities/post (данные) +
features/toggle-favorite (кнопка) + features/load-post-details.

Добавь это в R-10 и в FSD-раздел architecture.md.
· Skill требует для каждого инварианта тест или явную причину без теста.
R-13 разрешает только тесты сортировки и загрузки списка. Инварианты 2
(seed при обогащении) и 3 (детали: кэш / ошибка / повтор) остаются без
тестов. Как быть? → Расширяем R-13: юнит-тест на каждый инвариант.
Дополнительно к сортировке и загрузке списка:
- обогащение: у каждого поста есть seed, URL 32×32 и 300×300 строятся из
одного seed; для уже загруженного списка обогащение не перезапускается. В
тестах фиксируем faker.seed для детерминированности.
- load-post-details: есть в кэше — запроса нет; ошибка — ничего не
сохранено и следующий вызов запрашивает снова; успех — детали и URL
сохранены, следующий вызов не запрашивает.
Ограничения прежние: только юнит-тесты логики на Jest с моком api, без
компонентных тестов и без отдельных тестов api-слоя.
```

```text
перекрашивается. Обнови architecture.md.
· Ревьюер п.5–6. R-13 теперь говорит «юнит-тест на каждый инвариант», но
инвариант 5 (нет pull-to-refresh и кнопки сброса) и «faker не вызывается
при рендере» проверяет ревьюер. Кроме того, нет теста на сам gate
(useStoresHydrated), а у loadPostDetails нет проверки гидрации. Как быть? →
1. Инвариант 5 и «faker не вызывается при рендере» проверяем через ESLint,
а не тестами:
   - no-restricted-syntax: запрет JSX-атрибутов onRefresh и refreshControl;
   - no-restricted-imports: @faker-js/faker разрешён только в модуле
обогащения постов.
   Сообщения правил — со ссылкой на инвариант. Ревьюер дополнительно
проверяет, но основная гарантия — lint.
2. Gate: логику выносим в чистую функцию (список persist-сторов → все
гидрированы?) и тестируем её. Хук useStoresHydrated — тонкая обёртка, без
теста.
3. Гидрацию гарантирует только gate: навигатор (и все экраны) рендерится
после гидрации. loadPosts и loadPostDetails проверку гидрации не делают.
Тест «до гидрации запрос не уходит» заменяем тестом gate.
4. Обнови R-13: для каждого инварианта указан способ проверки — юнит-тест,
lint-правило или структурная гарантия с объяснением.
· Q19 и п.9: что показывает gate гидрации и что делать, если гидрация упала
(повреждённый JSON, ошибка migrate)? Сейчас в zustand 5.0.15 gate в этом
случае ждёт вечно. → Q19:
1. Пока gate ждёт, показываем пустой View с фоном темы, без спиннера: с
синхронным MMKV ожидание мгновенное, нативный сплэш его закрывает.
2. Ошибка гидрации (битый JSON, ошибка migrate) = данные отсутствуют. В
onRehydrateStorage при ошибке: удалить ключ стора из MMKV, сбросить стор в
начальное состояние, в dev залогировать ошибку. Приложение продолжает
работу как при первом запуске.
3. Gate ждёт не persist.hasHydrated(), а собственный признак «гидрация
завершена» (успех или восстановление), который ставится в
onRehydrateStorage в обоих случаях. Чистая функция gate работает с этим
признаком.
4. Тесты: восстановление при битых данных (ключ удалён, стор в начальном
состоянии, признак завершения стоит) — проверь на реальном поведении
zustand 5.0.15, что ошибка парсинга действительно доходит до
onRehydrateStorage. В тест gate добавь случай «восстановлено после ошибки».
5. Допущение для README: при повреждённых сохранённых данных они
сбрасываются, и приложение загружает список заново.
```

## Ответы на вопросы агента, раунд 5

_Уточнение: пустой массив для валидации._

```text
· В ответе пустой массив назван невалидным для validatePosts. Но по R-4
пустой массив и невалидный ответ показывают разное: пустой → «No posts» +

обрабатывает loadPosts: [] → статус empty («No posts» + Retry), флаг
«список загружен» не ставится. Невалидная структура → статус error. В тесте
validatePosts пустой массив — валидный случай; в тесте loadPosts —
отдельные случаи для empty и error.
```

```text
`userId: number`, хотя userId не проверяется. Тип обещает то, что не
проверено. Как типизировать результат? → validatePosts / validatePost
возвращают тип с проверенными полями: Pick<PostDto, 'id' | 'title' |
'body'> (можно назвать ValidatedPostDto). Маппер в Post принимает этот тип.
PostDto остаётся описанием контракта API.

Вопросы уровня «как точнее типизировать» и недостижимые граничные случаи
дальше решай сам в рамках принятых решений и фиксируй в журнале. Если
ревьюер чист или остались только такие пункты — закрывай этап 3: запись в
журнале и итоговый отчёт.
```
