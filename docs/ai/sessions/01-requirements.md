     # Требования: lorem-feed

     Источник — текст тестового задания. Документ разделяет требования на явные
     (прямо написаны в задании), неявные (следуют из смысла задания или здравого
     смысла) и неоднозначности, по которым нужно решение. Ссылки вида **[Q7]**
     ведут на вопросы в конце.

     ## 1. Цель

     Мобильное приложение для iOS и Android: список постов, экран деталей поста,
     избранное. Избранные посты поднимаются вверх списка. Данные загружаются
     один раз и сохраняются между запусками.

     ## 2. Явные требования

     ### 2.1 Стек
     | ID | Требование |
     |----|------------|
     | T-1 | React Native >= 0.77, bare (React Native CLI), **не Expo** |
     | T-2 | TypeScript |
     | T-3 | React Navigation >= 7 |
     | T-4 | FakerJS (`@faker-js/faker`) для изображений |
     | T-5 | State-manager обязателен (любой) |
     | T-6 | Чистая архитектура: разделены UI, логика, состояние |
     | T-7 | Платформы: iOS и Android |
     | T-8 | Дизайн произвольный |

     ### 2.2 Экран PostsScreen (рис. 1)
     | ID | Требование |
     |----|------------|
     | F-1 | Список постов из `GET https://jsonplaceholder.typicode.com/posts` |
     | F-2 | Каждый пост обогащён изображением 32×32 из FakerJS |
     | F-3 | Избранные посты визуально выделены |
     | F-4 | Избранные посты находятся вверху списка |
     | F-5 | Нажатие на пост открывает DetailsScreen (следует из «каждый пост
     можно открыть в отдельном экране») |

     ### 2.3 Экран DetailsScreen (рис. 2)
     | ID | Требование |
     |----|------------|
     | F-6 | Пост из `GET https://jsonplaceholder.typicode.com/posts/{id}` |
     | F-7 | Пост обогащён изображением 300×300 из FakerJS |
     | F-8 | Динамическая кнопка-переключатель: первое нажатие добавляет в
     избранное, повторное удаляет |

     ### 2.4 Данные и персистентность
     | ID | Требование |
     |----|------------|
     | D-1 | Список запрашивается только 1 раз и никогда не обновляется |

     деталей |
     | D-3 | При повторном запуске данные берутся из хранилища, повторно не
     запрашиваются |
     | D-4 | Избранное сохраняется между запусками и отображается сразу при
     старте |

     ## 4. Неоднозначности

     ### A1. Рисунки 1 и 2
     В задании упомянуты «рис. 1» и «рис. 2», но их нет в тексте. Дизайн при
     этом «произвольный». → **[Q1]**

     ### A2. Как получать изображение из FakerJS
     - **a)** `faker.image.url({ width, height })`: сетевая картинка (picsum).
     Без seed она случайна при каждой загрузке, нужен детерминированный URL
     (I-4).
     - **b)** `faker.image.urlPicsumPhotos({ width, height })` /
     `urlLoremFlickr(...)`: то же, но с явным провайдером.
     - **c)** `faker.image.dataUri({ width, height })`: SVG data URI, работает
     офлайн, но картинка абстрактная (однотонный фон) и не фото.
     - **d)** `faker.image.avatar()` для 32×32: размер не задаётся, масштабируем
     в UI.

     Связанный вопрос: картинка 300×300 на деталях — **та же самая** картинка в
     другом размере (один seed) или **независимая**? → **[Q2]**

     ### A3. Когда и как ходить в `/posts/{id}`
     Данные поста уже есть в ответе `/posts`, но F-6 прямо требует отдельный
     эндпоинт. С D-1/D-3 («не запрашивать повторно») это можно совместить
     по-разному:
     - **a)** Лениво: запрос при первом открытии конкретного поста, результат (и
     картинка 300×300) кэшируется навсегда. Если пост не открывали ни разу, без
     сети детали не откроются.
     - **b)** Сразу после загрузки списка заранее загрузить все 100 постов
     (`/posts/{id}`), потом не ходить в сеть совсем.
     - **c)** Сначала показать данные из списка, а `/posts/{id}` запросить один
     раз в фоне.

     → **[Q3]**

     ### A4. «Запрашивается только 1 раз и никогда не обновляется»
     - Нужен ли pull-to-refresh? Буквально запрещён.
     - Если первая загрузка упала, можно ли повторить (кнопка «Повторить»)?
     - Нужен ли проверяющему способ сбросить данные (dev-кнопка /
     переустановка), чтобы увидеть первую загрузку ещё раз?
     - Генерировать картинки FakerJS случайно (свои на каждой установке) или
     детерминированно по `id` (`faker.seed(id)`, одинаковые на всех установках)?

     → **[Q4]**

     ### A5. Порядок внутри избранного
     - **a)** по `id`;
     - **b)** по времени добавления: новые сверху;
     - **c)** по времени добавления: старые сверху.

     → **[Q5]**

     ### A6. Визуальное выделение и где переключать избранное
     - Как выделять: фон / рамка / иконка-звезда / бейдж / отдельная секция
     «Избранное» с заголовком?
     - Переключать избранное только на DetailsScreen (буквально по заданию) или
     также из списка (иконка в строке)?

     → **[Q6]**

     ### A7. State-manager и хранилище
     Варианты state-manager: Redux Toolkit, Zustand, MobX, Effector, Jotai.
     Варианты персистентности: AsyncStorage, MMKV; через `redux-persist` /
     `zustand/persist` или своей прослойкой.
     Отдельно: можно ли использовать RTK Query / TanStack Query для запросов и
     кэша, или запросы должны идти через «чистый» state-manager?
     → **[Q7]**

     ### A8. «Динамическая кнопка-переключатель»
     - Где кнопка: в хедере (`headerRight`) или в теле экрана?
     - Что значит «динамическая»: меняются текст и иконка, или нужна анимация
     (scale/цвет/haptic)?
     - Вид: кнопка с текстом («В избранное» / «Убрать из избранного»),
     иконка-сердечко/звезда или `Switch`?

     → **[Q8]**

     ### A9. Поведение деталей при загрузке/ошибке
     Можно ли добавить пост в избранное, пока `/posts/{id}` ещё грузится или
     запрос упал (данные из списка уже есть)?
     → **[Q9]**

     ### A10. Содержимое экранов
     - PostsScreen: аватар 32×32 + заголовок, или ещё превью `body` (сколько
     строк)? Показывать `userId`?
     - DetailsScreen: картинка 300×300 + `title` + `body`, или ещё
     `userId`/`id`?
     - Заголовки экранов в навигации.

     → **[Q10]**

     ### A11. «Чистая архитектура»
     - **a)** Feature-Sliced Design (app / pages / widgets / features / entities
     / shared).
     - **b)** Классическая Clean Architecture: domain (entities, use cases,
     repository interfaces) / data (API, storage, mappers) / presentation
     (screens, hooks, store).
     - **c)** Простое послойное разделение: `api/`, `store/`, `screens/`,
     `components/`, `hooks/`.

     → **[Q11]**

     ### A12. «Установить одной командой, запустить второй»
     - На iOS после `install` обязательно нужен `pod install`, его можно
     спрятать в `postinstall` или в отдельный скрипт `setup`.
     - Запуск: `npm run ios` / `npm run android` — это две разные команды под
     две платформы. Достаточно ли этого?
     - Предполагаем, что у проверяющего уже настроены Xcode / Android SDK /
     эмулятор, или нужна инструкция по окружению?
     - Пакетный менеджер: npm / yarn / pnpm?
     - Прикладывать ли собранный APK (GitHub Releases) как запасной вариант?

     → **[Q12]**

     ### A13. Артефакты AI-only подхода
     - Формат: экспорт чатов (markdown/JSONL), скриншоты, или и то и другое?
     - Где хранить: в репозитории (`docs/ai/`), отдельно, или в README ссылкой?
     - «Правила»: `CLAUDE.md`, skills, `.cursorrules` и т.п. — класть в
     репозиторий как есть?
     - Должен ли этот документ (`requirements.md`) и последующие планы входить в
     артефакты?

     → **[Q13]**

     ### A14. Версии и качество
     - RN: ровно 0.77 или последняя стабильная (>= 0.77)? New Architecture
     включена?
     - Нужны ли тесты (unit для стора/сортировки/репозитория, component-тесты)?
     - ESLint + Prettier, `tsc --noEmit` в скриптах? CI (GitHub Actions)?

     → **[Q14]**

     ### A15. UX-детали
     - Язык интерфейса: русский или английский? Язык README?
     - Тёмная тема: поддерживать / только светлая?
     - Плейсхолдер и fallback для картинок, пока грузятся / если не загрузились?
     - Кэшировать сами картинки на диск, чтобы они были видны офлайн (например,
     `@d11/react-native-fast-image`), или достаточно системного кэша `Image`?
     - Скролл списка после возврата с деталей, когда пост переехал наверх:
     сохранять позицию или скроллить к началу?

     → **[Q15]**
