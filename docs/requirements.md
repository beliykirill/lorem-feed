# Требования: lorem-feed

Источник — текст тестового задания. Документ разделяет требования на явные (прямо написаны в задании), неявные (следуют из смысла задания или здравого смысла) и неоднозначности, по которым нужно решение. Решения по неоднозначностям (R-*) собраны в разделе 5, допущения для README — в разделе 6, открытые вопросы — в разделе 7.

## 1. Цель

Мобильное приложение для iOS и Android: список постов, экран деталей поста, избранное. Избранные посты поднимаются вверх списка. Данные загружаются один раз и сохраняются между запусками.

## 5. Принятые решения

### R-1. Дизайн и содержимое экранов (Q1, Q10)
Рисунков 1 и 2 в задании нет, дизайн произвольный.
- **PostsScreen**, элемент списка: аватар 32×32, `title`, превью `body` в 2 строки. Избранные элементы визуально выделены (R-6).
- **DetailsScreen**: картинка 300×300 (не растягивается, скругление и мягкая тень), строка метаданных «Post #{id}», `title`, `body`; кнопка-переключатель избранного — звезда в шапке (R-7).

### R-2. Генерация изображений (Q2, Q16)
- У поста одна картинка, в списке и в деталях она одинаковая, отличается только размер: 32×32 в списке, 300×300 в деталях.
- При обогащении списка для каждого поста **один раз** генерируется seed через `faker.string.alphanumeric` и сохраняется вместе с постом.
- URL строится из seed чистой функцией `buildImageUrl(seed, width, height)` → `https://picsum.photos/seed/{seed}/{width}/{height}`. Функция детерминирована и не обращается к faker.
  - 32×32 — при обогащении списка, сохраняется вместе с постом;
  - 300×300 — на DetailsScreen показывается сразу, URL собирается той же функцией из seed, сохранённого с постом. Ждать ответа `/posts/{id}` не нужно. После первого успешного ответа `/posts/{id}` URL 300×300 сохраняется в запись деталей (R-3): это формальное обогащение ответа, и экран берёт URL оттуда, если запись уже есть.
- При рендере seed не генерируется, faker не вызывается. Seed только читается из стора.
- Проверено 2026-10-07: picsum по одному seed отдаёт одно и то же изображение в разных размерах. Например, `seed/jOx8D/32/32` и `seed/jOx8D/300/300` перенаправляют на `id/1010` (`fastly.picsum.photos/id/1010/32/32.jpg` и `.../id/1010/300/300.jpg`).
- Длина seed выбирается при реализации.

### R-3. Загрузка деталей поста (Q3)
- При открытии DetailsScreen пост сразу показывается из данных списка, картинка 300×300 — из seed поста (R-2).
- Если деталей поста ещё нет в кэше, `/posts/{id}` запрашивается один раз в фоне. Загрузка и ошибка на экране не отображаются (I-1).
- После успешного ответа детали и URL картинки 300×300 (из seed поста, R-2) сохраняются в стор (с персистентностью). Дальше пост показывается только из кэша, в сеть за ним не ходим.
- При ошибке ничего не сохраняется. Ошибка логируется в dev-сборке, запрос повторяется при следующем открытии этого поста и так до первого успешного ответа.
- Логика живёт в `features/load-post-details` (R-10).
- Защитное поведение: детали сохраняются только для поста, который есть в списке, иначе ничего не сохраняется, в dev — предупреждение. Сейчас путь недостижим: детали открываются только из списка. Проверка нужна для целостности стора: без поста нет seed для картинки 300×300. Отдельного теста нет: проверка — обычная ветка в коде, а структурно гарантировано то, что путь недостижим.
- Ответ `/posts/{id}`, в котором `id` не совпадает с запрошенным `postId`, — невалидный: ничего не сохраняется, это обрабатывается как ошибка, повтор при следующем открытии. Проверка — в валидации деталей (`validatePost` с ожидаемым `id`). Проверка кэша и сохранение деталей идут по одному ключу — запрошенному `postId`.
- Заранее все посты не загружаем: детали подгружаются только по факту открытия. Список виртуализирован (I-7).

### R-4. Однократная загрузка списка (Q4)
- Если первая загрузка `/posts` упала — экран ошибки с кнопкой «Retry». После первого успешного ответа список в сеть больше не запрашивается.
- Успешным считается только непустой валидный ответ. Однократно запрашивается именно непустой валидный список.
  - Пустой массив — не успех: флаг «список загружен» не ставится, ничего не сохраняется, на PostsScreen показывается пустое состояние «No posts» с кнопкой «Retry».
  - Невалидный ответ (не массив; элемент без числового `id` или без строковых `title`, `body`) — ошибка загрузки: экран ошибки с «Retry», ничего не сохраняется.
- **Модель поста (Q20).** DTO в api-слое описывает ответ API как есть, включая `userId`. Доменная модель `Post` = используемые поля API (`id`, `title`, `body`) + данные обогащения (`seed`, `thumbnailUrl`, R-2). Валидация проверяет только поля, которые попадают в модель, и возвращает новый объект только с ними: `ValidatedPostDto = Pick<PostDto, 'id' | 'title' | 'body'>`. Так `userId` отбрасывается уже при валидации, и для списка, и для деталей. Маппер в `Post` принимает этот тип, `PostDto` остаётся описанием контракта API.
- Pull-to-refresh нет.
- Кнопки сброса данных в UI нет. В README описано, как сбросить: переустановить приложение или очистить его данные.
- Картинки случайные на каждую установку, без `faker.seed(id)`. Генерируются один раз и сохраняются (R-2).

### R-5. Сортировка (Q5)
- Избранные посты идут первыми, между собой — по `addedAt` по убыванию (недавно добавленные выше).
- Для избранного хранится `id` поста и `addedAt` (время добавления).
- Неизбранные посты идут в исходном порядке ответа API. Пост, убранный из избранного, возвращается на исходное место.

### R-6. Избранное в списке (Q6)
- Переключать избранное можно только на DetailsScreen, как в задании. В списке переключателя нет.
- Выделение избранного в строке списка: затемнённый фон строки и иконка-звезда.
- Иконки — unicode-символы ★ (U+2605) и ☆ (U+2606) в `Text`, без новых зависимостей. Компонент `shared/ui/StarIcon` с пропсами `filled`, `size`, `color`, цвет из темы. Именно эти символы, а не эмодзи ⭐: эмодзи не перекрашивается.

### R-7. Кнопка-переключатель (Q8)
- Расположение: звезда в шапке DetailsScreen справа (`headerRight`). `pages/details` ставит её через `navigation.setOptions`, сама кнопка — из `features/toggle-favorite`.
- Динамика: иконка ☆ → ★ (`StarIcon`, R-6), цвет меняется на акцентный (`colors.star`), scale-анимация при нажатии на стандартном `Animated`, без новых зависимостей.
- Accessibility: `accessibilityRole="button"`, подпись «Add to favorites» / «Remove from favorites», `accessibilityState={{ selected }}`.
- **Изменено автором 2026-10-08** (этап 6). Было: кнопка с текстом «Add to favorites» / «In favorites» в теле экрана под текстом поста. Причина: в мобильных приложениях действие «в избранное» живёт в шапке, кнопка в потоке контента читается как отправка формы.

### R-8. Избранное во время загрузки деталей (Q9)
Переключать избранное можно всегда: оно привязано к `id`, данные из списка уже есть. Состояние фонового запроса `/posts/{id}` на кнопку не влияет.

### R-9. Состояние и хранилище (Q7)
- Состояние в Zustand, персистентность — middleware `persist` поверх `react-native-mmkv`.
- RTK Query и TanStack Query не используются. Запросы идут через api-слой сущности, состояние хранится в Zustand.
- **Проверка совместимости** (по данным npm и документации на 2026-10-07):

  | Пакет | Последняя версия | Требования |
  |-------|------------------|------------|
  | `react-native` | 0.87.1 | — |
  | `react-native-mmkv` | 4.3.2 | RN >= 0.76, нужен `react-native-nitro-modules` (peer dependency) |
  | `react-native-nitro-modules` | 0.37.1 | RN >= 0.75, Xcode >= 16.4, Swift >= 5.9, Android `compileSdkVersion` >= 34, NDK >= 27 |
  | `zustand` | 5.0.15 | — |

  MMKV v4 — Nitro Module на JSI, без старого Bridge, так что с New Architecture он совместим. RN 0.87.1 укладывается в требования MMKV и Nitro. Нюанс: в devDependencies MMKV 4.3.2 собран и протестирован с RN 0.85.3, а не 0.87, а peer dependencies указаны как `*`, так что формальной гарантии для 0.87 нет. Проверено на этапе каркаса 2026-10-08: с MMKV 4.3.2 и Nitro 0.37.1 приложение собирается и запускается на iOS (Xcode 26.3, симулятор) и Android (эмулятор, API 37).
- API MMKV v4 для адаптера `persist`: `createMMKV()`, `getString(key)`, `set(key, value)`, `remove(key)` (в v4 `delete` переименован в `remove`). В пакете есть `createMockMMKV` — пригодится для Jest.
- Запрос списка не уходит, пока все persist-сторы не завершили гидрацию из MMKV: иначе при повторном запуске список запросился бы повторно (D-3).
- **Сторы.** Два persist-стора, по одному на сущность:
  - `entities/post` — список, детали по `id`, статус загрузки списка;
  - `entities/favorite` — `Record<id, addedAt>`.

  У каждого свой ключ в MMKV и свой `version` для будущих миграций. Через `partialize` персистятся только данные и флаг «список успешно загружен». Статусы загрузки и ошибки не персистятся.
- **Gate гидрации.** В `app` gate работает с явным списком трекеров гидрации, по одному на persist-стор. Навигация рендерится, только когда гидрация завершилась у всех. С синхронным MMKV гидрация завершается сразу при создании стора (проверено на zustand 5.0.15, см. `docs/architecture.md`). Gate всё равно остаётся явным: он фиксирует инвариант и не зависит от выбора хранилища. Трекер создаётся как `createHydrationTracker(storage, key)` и получает хранилище аргументом, поэтому к MMKV не привязан (I-8).
  - Gate ждёт не `persist.hasHydrated()`, а собственный признак «гидрация завершена» каждого стора. Признак ставится в пост-колбэке, который возвращает фабрика `onRehydrateStorage`, и при успехе, и после восстановления. Причина: при ошибке гидрации `hasHydrated()` в zustand 5.0.15 навсегда остаётся `false`.
  - Логика gate — чистая функция `isGateOpen(trackers)` (все признаки стоят?). Подписку на трекеры даёт `createHydrationGate(trackers)`. Объект gate создаётся один раз на уровне модуля, со списком трекеров. Хук `useStoresHydrated` без аргументов — тонкая обёртка над ним через `useSyncExternalStore`.
  - Пока gate ждёт, показывается пустой `View` с фоном темы, без спиннера: с синхронным MMKV ожидание мгновенное, его закрывает нативный сплэш.
  - Гидрацию гарантирует только gate: навигатор и все экраны рендерятся после неё. `loadPosts` и `loadPostDetails` гидрацию не проверяют.
- **Ошибка гидрации (Q19)** — битый JSON или исключение в `migrate` — означает, что сохранённых данных нет. При ошибке пост-колбэк трекера удаляет ключ стора из хранилища, в dev-сборке ошибка логируется. Стор остаётся в начальном состоянии: zustand при ошибке его не меняет (проверено). Восстановление идёт по каждому стору отдельно: повреждён список — он загрузится заново, повреждено избранное — оно очистится.

### R-10. Архитектура (Q11)
Feature-Sliced Design, адаптированный под React Native:

| Слой | Содержимое |
|------|------------|
| `app` | провайдеры, навигация, гидрация сторов (gate до первой загрузки) |
| `pages` | `PostsScreen`, `DetailsScreen` |
| `widgets` | `posts-list` — список постов и селектор сортировки |
| `features` | `toggle-favorite`; `load-posts` (логика «загрузить один раз»); `load-post-details` (детали, если их нет в кэше) |
| `entities` | `post` — модель, api, обогащение картинками, UI-карточка; `favorite` — стор избранного |
| `shared` | http-клиент, обёртка над MMKV и трекер гидрации, типы маршрутов, тема, UI-кит |

Правило импортов FSD: слой импортирует только из слоёв ниже; между слайсами одного слоя — только через public API (`index.ts`).

- `features/load-post-details` симметричен `features/load-posts`: проверка кэша, однократный запрос `/posts/{id}`, сохранение деталей и URL 300×300.
- Селектор сортировки объединяет две сущности, поэтому живёт не в `entities`, а в `widgets/posts-list/model`: чистая функция `(posts, favorites) → отсортированный список с флагом isFavorite` и хук поверх сторов.
- Карточка поста в `entities/post/ui` получает `isFavorite` пропсом и про стор избранного не знает.
- `enrichPosts` не входит в public API `entities/post`. Наружу отдаются только операции «обогатить и сохранить»: `savePostList(dtos)` и `savePostDetails(postId, dto)`. Вместе с lint-запретом глубоких импортов это структурная гарантия того, что `enrichPosts` и faker нельзя вызвать напрямую снаружи слайса. То, что `savePostList` вызывается только в `features/load-posts`, — договорённость с проверкой ревьюером, lint-правила для неё нет.
- Правило импортов закреплено lint-плагином `eslint-plugin-boundaries` (dev-зависимость, одобрена автором 2026-10-08): импорт только вниз по слоям, между слайсами одного слоя — только через public API. Плагин ловит и импорты через имя слоя, и относительные пути из соседнего слайса. Импорт внутренних модулей своего слайса разрешён, в том числе в тестах.
- **Алиас `@/` → `src/`** (решение автора 2026-10-08, этап каркаса): импорты между слайсами и слоями пишутся как `@/entities/post`. Причина — читаемость импортов между слоями. Алиас один, отдельных алиасов по слоям нет; внутри слайса импорты относительные. Алиас задан в `tsconfig.json` (`paths`) и `babel.config.js` (`babel-plugin-module-resolver`, для Metro и Jest); `eslint-plugin-boundaries` резолвит его через `eslint-import-resolver-typescript`. Обе dev-зависимости одобрены автором 2026-10-08.
- `pages/details` собирает `entities/post` (данные), `features/toggle-favorite` (кнопка) и `features/load-post-details`.
- Типы маршрутов (`RootStackParamList`) и константы имён маршрутов лежат в `shared/config/navigation`, `app/navigation` и `pages` импортируют их оттуда. Навигацией управляют только `pages`: `widgets/posts-list` получает колбэк `onPostPress(id)` и про навигацию не знает.

### R-13. Версии и качество (Q14)
- React Native — последняя стабильная (на 2026-10-07 это 0.87.1, см. R-9), New Architecture включена.
- Для каждого инварианта указан способ проверки: юнит-тест, lint-правило или структурная гарантия с объяснением. Сводная таблица — в `docs/architecture.md`, раздел 6.
- Юнит-тесты (Jest, api замокан):
  - селектор сортировки (чистая функция): избранные сверху, новые первыми, после удаления из избранного пост возвращается на исходное место;

Исключение для api-слоя этот тест не затрагивает;
  - обогащение (`enrichPosts` и `toPostDetails`, тест импортирует внутренний модуль своего слайса): у каждого поста есть seed, URL 32×32 и 300×300 строятся из одного seed (`userId` к этому моменту уже отброшен валидацией). `faker.seed` в тестах фиксируется для детерминированности. «Для уже загруженного списка обогащение не перезапускается» проверяет тест загрузки списка;

  - gate: чистая функция `isGateOpen` и `createHydrationGate` над признаками гидрации, включая случай «восстановлено после ошибки». Заменяет тест «до гидрации запрос не уходит»: инвариант 4 держится на gate;
  - восстановление при битых данных на реальном `persist` zustand 5.0.15 с мок-хранилищем, переданным в трекер: ключ удалён, стор в начальном состоянии, признак завершения стоит.
- Lint-правила (ESLint из шаблона + одобренный `eslint-plugin-boundaries`), сообщения со ссылкой на инвариант:

## 6. Допущения для README

- **Детали поста.** Задание требует брать пост из `/posts/{id}` и запрашивать данные только один раз. Мы трактуем это так: при первом открытии пост сразу показывается из данных списка вместе с картинкой 300×300, а `/posts/{id}` запрашивается один раз в фоне. Фоновый запрос на экране никак не отображается: он возвращает те же поля, что уже показаны. После успеха детали и URL картинки 300×300 кэшируются навсегда, при ошибке запрос повторится при следующем открытии. Заранее все посты не загружаются.
- **Картинки.** У поста одна картинка: в списке она 32×32, в деталях та же самая в 300×300. Seed генерируется через `faker.string.alphanumeric` один раз при первой загрузке списка и хранится вместе с постом. Оба URL picsum строятся из него (`https://picsum.photos/seed/{seed}/{w}/{h}`), поэтому изображение не меняется ни между экранами, ни между запусками. Картинки случайные для каждой установки. Без сети картинки, которые ещё не попали в системный кэш, не загрузятся, вместо них показывается fallback.
- **Однократная загрузка.** Pull-to-refresh нет. Если первая загрузка упала, её можно повторить кнопкой на экране ошибки. Пустой ответ API не считается успешной загрузкой: показывается «No posts» с кнопкой повтора. Невалидный ответ считается ошибкой. Один раз загружается непустой валидный список.
- **Сброс данных.** Кнопки сброса в приложении нет. Чтобы увидеть первую загрузку заново, переустановите приложение или очистите его данные (Android: Settings → Apps → lorem-feed → Storage → Clear data; iOS: удалить и установить заново).
- **Повреждённые данные.** Если сохранённые данные повреждены и не читаются, они сбрасываются, причём по отдельности: повреждён список — он загрузится заново, повреждено избранное — оно очистится.
- **Избранное.** Переключается только на экране деталей. Избранные посты идут первыми, недавно добавленные выше.
- **Окружение.** Предполагается, что Xcode, Android SDK и эмулятор уже настроены (ссылка на официальный гайд).
- **Дизайн.** Рисунков 1 и 2 в задании нет, дизайн произвольный.
